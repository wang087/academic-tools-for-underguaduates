## 1. 适用场景

| 场景 | 是否适用 |
|---|---|
| 已拿到某作者 **≥10 篇**论文的题录（+ 部分全文），要产出解读报告 | ✅ 适用 |
| 论文数 < 10 篇 | ❌ 直接由主 agent 顺序解读更省事（subagent 开销不值） |
| 需要**逐篇深读**（方法论 / 结论 / 关键信息 / 量化数据） | ✅ 适用 |
| 只需按题名做相关性打分筛选 | ❌ 本手册不是筛选工具 |
| 还没拿到全文 | ❌ 先回主流程 §4 阶段 E 用 CDP 下载；**不要**自行取全文 |
| **阶段 H2**：已由 `refs_curate.py` 整理出最终文献列表，要做**研究方向综述** | ✅ 适用 —— 用 §7.1 的**综述网络版**提示词；任务包在 `.work_cdp/refs/tasks/` |
| 阶段 H2 但文献只有题录、无摘要 | ⚠️ 仍可做，但证据层级只能标 `metadata-only`，报告须如实披露 |
| **阶段 R2（v8）**：已由阶段 R 选出 6–12 篇优质综述，要做**本科生领域概貌** | ✅ 适用 —— 用 §7.2 的**领域概貌版**提示词；任务包在 `.work_cdp/reviews/tasks/`。★ 读者是**没有科研经验的本科生**，要求解释术语、给出阅读顺序 |
| 想做「去重 / 剔除无关文献」 | ❌ 那是 `refs_curate.py` 的职责，不是本手册 |

## 2. 为什么要并行 subagent

解读一篇论文需要通读全文（动辄 1–4 万字符）。20 篇论文 ≈ 40 万字符，
**远超单个上下文窗口**，硬塞会导致后半程被截断、结论质量断崖式下跌。

并行 subagent 解决两件事：

1. **上下文隔离** —— 每篇论文在独立的干净上下文里精读，不受其他论文干扰；
2. **吞吐** —— 各篇互不依赖，可同时推进，墙钟时间 ≈ 最慢的一篇而非总和。

代价是 token 成本上升，因此 §1 给了适用门槛（≥10 篇才值得）。

## 3. 铁律（继承主流程，不得违反）

| # | 铁律 | 在本阶段的含义 |
|---|---|---|
| 1 | **分层获取策略（§5.1）** | subagent **不得**发起任何网络请求。任务包里**已经**备好：作者论文的本地 PDF 文本、参考文献的摘要，以及**开放获取综述的全文**（阶段 D2 通过 Europe PMC 结构化接口取好的，见 `evidence.source`）。缺什么就用现有层级解读，并**如实标注**证据层级。**禁止** subagent「顺手用 curl/urllib 补一篇」—— 那既越界，也破坏可复现性。 |
| 2 | **鼠标自动化禁令** | 本阶段不涉及浏览器，天然不适用；但**不得**为「看得更清楚」去驱动浏览器截图。 |
| 3 | **不臆造** | 论文里没写的数字、结论、机制，**一律不得**出现在解读卡里。拿不准就写进 `open_questions` 或留空。 |
| 4 | **区分「已验证结论」与「作者主张」** | `verified_conclusions` 只收**有数据/实验支撑**的结论；纯推测、展望、未做的设想归入 `open_questions`。 |
| 5 | **保留原文数值** | 量化数据必须**原样引用**（含单位、条件、基线），不得换算、不得四舍五入、不得改写措辞。 |

## 5. 执行流程

```
① prepare   uv run --with pypdf python 流程1/scripts/interpret_prepare.py
                 ↓  产出 tasks/*.json（每篇一个自包含任务包）
② 分派      主 agent 分批并行（单条消息内多个 Agent 调用），每批 30–60 秒轮询一次完成度
                 ↓  每个 subagent 只读自己的 task.json，只写自己的 result.json
③ 回收      主 agent 逐份校验 schema 与完整性（坏卡打回重做，不迁就）
④ build     uv run python 流程1/scripts/interpret_build.py
                 ↓  时间线 / 逐篇卡片 / 关键词统计 / 研究方向 / 方法范式
⑤ 复核      完整性批评：哪些篇缺卡？哪些是摘要级？哪些方向明显缺席？
```

### ① prepare

```bash
uv run --with pypdf python 流程1/scripts/interpret_prepare.py
# 可选：--max-chars=60000   单篇正文截断上限
# 可选：--only=10.1038/xxx,10.1016/yyy   只准备指定 DOI
# 可选：--no-text           只出题录与摘要（不读 PDF）
```

### ② 分派（**关键：并行 + 动态轮询**）

**必须**在**同一条消息**里发出多个 Agent 调用，否则会退化成串行。

⛔ **不要盲等固定时长**（`sleep 150` / `sleep 200` 之类）再收子代理。
**分派 → 30–60 秒后查完成度 → 按剩余篇数决定下一批大小与下次间隔 → 重复。**

```bash
# 退出码即结论：0=齐了可 build / 3=仍在跑 / 4=有坏卡需重派 / 2=无任务包
uv run python 流程1/scripts/agent_poll.py --stage H      # 阶段 H
uv run python 流程1/scripts/agent_poll.py --stage H2     # 阶段 H2
uv run python 流程1/scripts/agent_poll.py --stage R2     # 阶段 R2
```

**批量与间隔不由 agent 手拍**，由脚本按实测剩余量给出：

| 剩余未回收 | 建议间隔 | 说明 |
|---|---|---|
| ≤ 2 篇 | 30 秒 | 就差最后一两篇，短间隔立刻收口 |
| 3–6 篇 | 45 秒 | 常规 |
| > 6 篇 | 60 秒 | 这一批还在跑，短间隔只是浪费轮次 |

**单批上限**：阶段 H / H2 每批 **≤ 6**；阶段 R2 每批 **≤ 4**。
上限来自实测 —— 并发过高会触发生成长度上限，产出**结构合法但内容是
`placeholder`** 的卡。

**动态调整三档**：

1. 上一批**全部顺利回收** → 下一批放到上限；
2. 上一批**有拒收/截断** → 下一批**减半**，该篇单独重派；
3. 连续两批都有坏卡 → 退回**每批 3 篇**。

> **轮询窗口不是空转窗口**：等待期间去做与该批无关的活
> （取全文、抽图、抽正文、组装下一阶段任务包）。详见主流程 §4.1 / §4.2。

### ③ 回收与校验

逐份检查（用脚本或人工）：

- [ ] `results/` 里文件数 == `tasks/` 里文件数（缺的**重派**）
- [ ] 每份都能 `json.loads` 且**含 schema 的全部必需键**（§ 6）
- [ ] `doi` 与任务包一致（防止 subagent 张冠李戴）
- [ ] `quantified_gains` 里的数字**能在原文中找到**（抽查 2–3 篇）
- [ ] 没有把「展望」写进 `verified_conclusions`

> **坏卡一律重派，不要手工修补。** 手工修补会让解读标准在批次间漂移。

### ④ build

```bash
uv run python 流程1/scripts/interpret_build.py
# 可选：--families=<keyword_families.json>   语义词族合并表
```

### ⑤ 完整性批评（不可跳过）

最后的复核 agent 只回答三个问题：

1. **哪些篇没有解读卡？** 原因是什么（无全文？准备失败？）
2. **哪些卡是「仅摘要」？** 在报告里是否已如实标注？
3. **有没有明显缺席的研究方向？**（对照 § 4.1 的题录年份分布）

## 6. 单篇解读规范（**用户指定的强制格式**）

每个 subagent 产出的解读卡**必须**严格按下面的 schema 写。
这是**用户明确给定的总结规则**，不得自行增删字段：

```json
{
  "doi": "10.1038/s41586-024-xxxxx",
  "one_line": "一句话定位：本文在作者研究脉络中的位置",
  "problem_solved": "本文有效解决了什么问题（1–3 句）",
  "methods": [
    "明确的方法论 —— 具体到用了什么体系/手段/模型，不要写「用了实验方法」这种空话"
  ],
  "verified_conclusions": [
    "经过验证的结论 —— 必须有数据/实验支撑；纯推测不得写在这里"
  ],
  "key_20": [
    "二八原则关键信息 —— 见下方说明"
  ],
  "quantified_gains": [
    {"metric": "指标名", "value": "提升幅度（原样引用，含单位）",
     "context": "对比基线 / 实验条件"}
  ],
  "open_questions": [
    "待验证的问题 / 作者自述的局限 / 尚未解决之处"
  ],
  "direction_tags": ["研究方向标签，2–4 个"],
  "paradigm_tags": ["方法范式标签，1–3 个"],
  "evidence": {"source": "fulltext 或 abstract", "text_chars": 12345}
}
```

### 6.0 解读档位（**v13 新增，先读 —— 决定每个字段写多深**）

**档位从哪来**：阶段 0（`prepare_stage.py`）确认，落盘在
`.work_cdp/prepare_plan.json`：

| 阶段 | 选项 key | 默认 |
|---|---|---|
| H（作者论文） | `interpret_tier` | **L2** |
| H2（研究方向综述） | `review_interpret_tier` | **L3** |
| R2（领域概貌） | `review_interpret_tier` | **L3** |

`interpret_prepare.py` / `refs_prepare.py` / `reviews_prepare.py` 会把它
**嵌进每个任务包**（字段名统一为 `interpret_tier`）。
**subagent 一律以任务包里的 `interpret_tier` 为准**，不要自己去问阶段 0。

查询（供人工核对）：`uv run python 流程1/scripts/prepare_stage.py --tier H`
（stdout 只有 `L1`/`L2`/`L3` 三选一）。

**三档是什么**：

| 档位 | 用途 | 特征 |
|---|---|---|
| **L1 精简** | 表格、清单、速览 | 只有摘要、主要成就、回顾展望；**不含**误差项、样本量、图表引用、实验步骤 |
| **L2 详细** | 逐篇卡片（阶段 H 默认） | 另加误差项、样本量、有限实验过程、排除性证据、局限 |
| **L3 完整** | 综述与代表作（H2/R2 默认） | 另加完整论证链、机制细节、逐条局限、作者语气标注 |

> ⛔ **最容易犯的错：以为"档位低就能说得更肯定"。**
> 三档只差**细节量**，不差**断言强度**。同一个发现在三档里的动词强度必须一致，
> 且与原文同级——L1 不因为地方小就把「提示」写成「证实」。
> 规范定义见 skill `paper-interpretation-writing`（含档位规范、句式库、
> 跨 agent 数据契约、以及一个可离线运行的校验器）。

**字段 × 档位**（同一张卡，按档位决定写多深）：

| 字段 | L1 | L2 | L3 |
|---|---|---|---|
| `one_line` | ✅ 1 句定位 | ✅ | ✅ + 点出在作者脉络中的位置 |
| `problem_solved` | ✅ 1–3 句：缺口 → 做了什么 → 最关键发现 | ✅ | ✅ + 补上排除的替代解释 |
| `methods` | ⚠️ 留 `[]`（L1 不写方法清单） | ✅ 点名到可复现 | ✅ 完整，含关键参数 |
| `verified_conclusions` | ⚠️ 只留 2–4 条最硬的 | ✅ 逐条挂证据 | ✅ 逐条挂证据 + 出处 |
| `key_20` | ✅ 3–5 句有序文字 | ✅ 3–8 句 | ✅ 3–8 句，含设问推进 |
| `quantified_gains` | ⚠️ 只留 2–5 个**结论性**数字，**不带误差项** | ✅ 含误差项、样本量、基线、出处 | ✅ 同 L2，逐条 |
| `open_questions` | ⚠️ 0–2 条 | ✅ | ✅ 逐条，含未做的实验与并列未区分的机制 |
| `direction_tags` / `paradigm_tags` | ✅ 受控词表 | ✅ | ✅ |
| `evidence` | ✅ 如实标注 | ✅ | ✅ |

> **L1 的"留空"是硬约束，不是偷懒**：阶段 H 的 L1 会渲染成表格与速览，
> 一个带误差项的测量值会让整张表失去逐行可比性。
> 拿不准某条算不算"结论性数字"时，问自己：**它能不能进一张表格的"关键数字"列？**

> ⚠️ **L1 的下游代价**：阶段 H 的关键词统计、阶段 K 的知识图谱与词云、
> 以及 `refs_curate.py` 的方向相关性打分，都从解读卡的 `methods` / `key_20` / 标签取语料。
> **L1 留空 `methods`**，这三处会明显变薄 —— 属预期内的取舍，不是缺陷。
> 需要知识图谱时建议用 L2 及以上。
> （这些消费者读的是 `interpret/results/*.json` **卡片**，不解析渲染后的 Markdown，
> 因此改档不会导致它们读取失败。）

### 6.1 Goals（为什么做这件事）

- 深入理解论文的**主旨、关键思路**和**待解决问题**；
- 为读者提炼出**最重要的关键信息**。

### 6.2 Constrains（硬约束）

- 遵循 **「二八原则」** 进行总结；
- 输出**阅读的总结文字**（不是罗列原文句子）。

### 6.3 Skills（需要的能力）

- 熟练阅读和理解学术论文的结构与内容；
- 总结和梳理**论文主旨、关键思路、待解决问题**；
- **细致入微**地分析论文细节。

### 6.4 Workflows（四个必答步骤）

> 这四步就是 schema 里那四个数组字段，**逐条落实、缺一不可**。

**1. 列出本文有哪些明确的方法论** → `methods`
把论文**实际使用**的方法论列清楚：实验体系、表征手段、计算模型、样本与对照设计、
统计方法、关键参数。要具体到可复现的程度，不要写「采用了多种方法」这类空话。

**2. 列出本文有哪些经过验证的结论** → `verified_conclusions`
只列**有证据支撑**的结论（实验数据、统计检验、对照结果）。
作者在讨论里的推测、展望、类比，**不属于**已验证结论。

**3. 关键信息（二八原则）** → `key_20`
> 「二八原则」是指：**本文有 20% 的内容是关键信息，这部分信息可以让我理解其他 80% 的内容。**

请把**那 20%** 整理成**有序的文字**（按逻辑顺序，不是随意罗列），内容包括但不限于：
- 论文主旨；
- 论文**有效解决了什么问题**；
- 论文有哪些**待验证的问题**。

**4. 优化 / 解决方案 / 提升等数据要着重列出** → `quantified_gains`
例如「提升了某方面的性能高达 10%」这类，**逐条列出**：

| 要点 | 要求 |
|---|---|
| 数值 | **原样引用**，含单位与有效数字，不得换算或改写 |
| 基线 | 相对什么对比（对照组的数值） |
| 条件 | 在什么条件下取得（温度/pH/样本量/数据集等） |
| 位置 | 注明出处（图 3b / 表 2 / 正文 p.7），便于回查 |

> 论文**没有**量化提升数据时，`quantified_gains` 写 `[]` 并在
> `limitations` 或 `open_questions` 里说明 —— **不要为凑字段编数字**。

### 6.5 标签必须取受控词表（**v7 新增**）

`direction_tags` / `paradigm_tags` 是**自由填写**的，而解读卡由**多个并行
subagent** 分别产出 —— 同一概念会写成
`machine-learning` / `machine learning` / `ML` / `机器学习`，
汇总时被拆成 4 条弱信号，「研究方向归纳」与「范式分析」两节直接失真（见 §8「标准漂移」）。

**规则**：

1. `.work_cdp/tag_vocabulary.json`（模板：`流程1/templates/方法范式标签词表.json`）
   会被 `interpret_prepare.py` / `refs_prepare.py` **嵌进每个任务包**；
2. 两个标签字段**必须**从任务包的 `tag_vocabulary` 里取词；
3. 确实没有合适的词时才自造，且**必须加前缀 `自定义:`** ——
   加前缀是为了让**词表缺词**与**标注漂移**在汇总时可区分；
4. 汇总脚本按「精确命中 → 别名 → 去连字符」三级归一，
   **未归一的标签保留原值并在报告中如实列出**，绝不静默丢弃。

| 维度 | 取值来源 | 数量 |
|---|---|---|
| `direction_tags` | `direction_tags_vocabulary`（领域维度） | 2–4 |
| `paradigm_tags` | `paradigm_tags_vocabulary`（做法维度） | 1–3 |
| `network_role`（仅 H2） | 奠基工作 / 方法源头 / 共识综述 / 争议焦点 / 最新进展 | 1 |

> `experimental` 与 `computational` 为**互斥范式**：同时出现时以篇数多者为准并告警 ——
> 一篇论文同时是"纯湿实验"与"纯计算"通常是标注错误。

### 6.6 综述网络扩展（**仅阶段 H2**）

阶段 H2 的解读卡在前述字段之上**再加两个**：

| 字段 | 含义 | 取值 |
|---|---|---|
| `network_role` | 这条文献在**整个研究方向**里扮演什么角色 | 奠基工作 / 方法源头 / 共识综述 / 争议焦点 / 最新进展 |
| `relation_to_author` | 该作者在哪些方面**沿用 / 扩展 / 对照**了本文 | 一两句自然语言 |

其余 11 个必需字段与阶段 H **完全一致** —— 同一套四步规范、同一条
「不为凑字段编数字」的铁律。`refs_build.py` 按 13 个必需字段校验。

## 8. 质量控制

| 风险 | 表现 | 对策 |
|---|---|---|
| **标准漂移** | 各 subagent 对「已验证结论」的松紧不一致 | 提示词里原样带上 § 6.2/§ 6.4 的约束文字，不要转述 |
| **幻觉数据** | `quantified_gains` 里出现原文没有的百分比 | 回收时抽查 2–3 篇回原文核对；发现即**全批重派** |
| **张冠李戴** | result 的 doi 与 task 不符 | 校验 `doi` 字段，不符即重派 |
| **静默缺卡** | 某篇没产出 result，汇总时被无声跳过 | build 时比对 tasks/results 数量并**显式列出缺卡清单** |
| **上下文溢出** | 任务包过大导致 subagent 读不完 | `interpret_prepare.py` 默认按 `--max-chars` 截断，并在包内标注 `text_truncated` |
| **并行写冲突** | 多个 subagent 写同一文件 | 一 task 一 result，文件名带序号+DOI；主 agent 独占汇总 |
| **档位漂移（v13）** | 同一批 subagent 各写各的深度，汇总后卡片深浅不一 | 提示词原样带上 § 6.0 的档位说明；任务包已嵌 `interpret_tier`，subagent 以它为准 |
| **档位越界（v13）** | L1 卡片里出现误差项、样本量、图表引用或实验步骤 | 回收时按 § 6.0 的「字段 × 档位」表校验；命中即重派。也可用 skill 的校验器：`check_interpretation.py <草稿> --tier L1` |
| **语气越档升级（v13）** | 为了"表格好看"把 L1 的「提示」写成「证实」 | 三档语气必须同级且与原文同级；逐条回查原文动词 |

## 9. 常见错误

- ❌ **串行分派**：一个一个发 Agent 调用 → 退化成串行，白付了并行的复杂度。必须同一条消息内多发。
- ❌ **把全文粘进提示词**：几十万字符直接塞爆主上下文。让 subagent 自己读 `tasks/*.json`。
- ❌ **让 subagent 自己去找全文**：会诱发「顺手 curl 一篇」→ **违反最高优先级禁令**。
- ❌ **让 subagent 更新共享汇总文件**：并发写必然互相覆盖。汇总只由主 agent 做。
